## Что нужно сделать бэкенду

1. **Личные логины сотрудников и преподавателей.** Если они подключаются к БД напрямую:
   ```sql
   CREATE ROLE <логин> LOGIN PASSWORD '...' IN ROLE deanery_staff;   -- или deanery_teacher
   UPDATE deanery.app_user SET db_login = '<логин>' WHERE login = '<логин в приложении>';
   ```
2. **Подключение приложения через одну служебную учётную запись.** Ей нужна роль `deanery_agent`. Тогда `app.user_id` по-прежнему передаётся в каждой транзакции. Решения по исправлению оценок через агента не выполняются, как и раньше: их директор принимает под своим логином.
3. **Служебные таблицы бэкенда** (токены, файлы, история чата) лучше держать в отдельной схеме. Новые функции владельца в этой базе по умолчанию недоступны `PUBLIC`, права на них нужно выдавать явно.

### Исправления в отчёте

- **Кратности.** Для директора указано 0..1 : 0..1 (UNIQUE), для подписанта 1 : 0..N (NOT NULL). Это совпадает с таблицами связей. Телефон контактного лица больше не называется уникальным.
- **Пояснения к правилам.** В раздел 2.2 добавлены:
  - состояния результата;
  - подгруппы;
  - будущее зачисление по приказу;
  - историческая принадлежность к группе;
  - историческая сумма стипендии;
  - кто действует в базе.
- **ЛП 1.** Добавлены правила, которые соблюдаются при изменениях данных: снятие старосты, увольнение куратора и заведующего, перевод заведующего.
- **Нормальная форма.** В разделе 5.1 обоснована НФБК по отношениям с ключами и функциональными зависимостями. Разобраны совпадения, которые нашёл `07_fd_scan.sql`.
- **Журнал изменений.** В таблице 1 раздела 5.2 пояснено, почему в тестовой базе журнал пуст.
- **Оформление** не менялось: отчёт сделан строго по шаблону (заголовки, подписи «Таблица 1–3», титул, без оглавления, колонтитулов и заключения).
