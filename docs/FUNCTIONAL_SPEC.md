# Функциональность в рамках существующего фронтенда

Ниже описан базовый текущий интерфейс. В целевой объём теперь включены серверная очередь решений, передача сотруднику, раздельное исполнение и manifest использования вложений. Полная актуальная спецификация с ролями и действиями — [DETAILED_IMPLEMENTATION_PLAN.md](DETAILED_IMPLEMENTATION_PLAN.md); реализация ждёт одобрения.

Фиксированная основа — `frontend/src` ветки **react-frontend** из `Lyaako/dean-agent-front`; [точная версия](FRONTEND_VERSION.md). Визуальная копия в `prototype` взята из `mockup/redesign` этой же ветки. OLAP сейчас демонстрация в макете и заглушка в React, но по прямому дополнению пользователя его полная реализация обязательна. Определения показателей/API согласуются по разделу 5.4 актуального плана; остальные базовые обращения определяются фактическими вызовами React.

## 1. Агент — основной инструмент

Сотрудник пишет задачу в существующем поле шапки. Чат раскрывается, показывает этапы и результат. Агент понимает русский запрос, учитывает принадлежащую пользователю сессию и последние сообщения, выбирает разрешённые инструменты, уточняет неоднозначное ФИО/группу/основание и сообщает только подтверждённые факты.

Чтение: поиск студентов, карточка и группа, успеваемость, записанные долги, результаты и ведомости, расписание, посещаемость, приказы и отпуска, стипендии, документы, практики, курсовые/ВКР, преподаватели и нагрузка, доступная история. Для сводок и подсчётов используются функции/представления БД. Наличие или отсутствие строки не доказывает юридическое состояние, использованные попытки или дату возникновения долга.

Нормативные вопросы: гибридный поиск BGE-M3/Qdrant, точная версия, название, источник и страница/пункт. Если документа нет — агент прямо сообщает это. Нормативный вывод не подменяет приказ и решение сотрудника.

Вложения: файл загружается, обрабатывается и связывается с текущим запросом по версии. Агент читает извлечённый текст/доступные визуальные страницы, указывает качество и сокращение, ссылается на файл и страницу. Следующие текстовые фрагменты доступны контролируемому инструменту только для вложений этого запуска.

Изменения: сохраняется исходный `propose_sql_change` для десяти таблиц — `document_request`, `academic_work`, `grade`, `attendance`, `grade_sheet`, `practice_placement`, `teaching_assignment`, `schedule_slot`, `organization_contact`, `contact_person`. Только разрешённые INSERT/UPDATE, одна рабочая запись, конкретные значения и основание пользователя. Предложение ничего не меняет до решения сотрудника.

Дополнительно агент получает подготовку шести workflows, уже существующих во фронтенде: зачислить, перевести, оформить отпуск, вернуть из отпуска, отчислить по явно заданному основанию, восстановить. Предпросмотр перечисляет приказ и связанные эффекты. Все обязательные реквизиты уточняются; агент не выдумывает подписанта. Для операций форм вне SQL-whitelist таблиц или полей используется ограниченная типизированная подготовка изменения person/employee/study_group, трёх разрешённых полей student и допустимых правок остальных форм, например item_id работы/практики. Исполнение происходит только после решения сотрудника через существующее окно предложений.

Никаких DELETE/DDL/терминала/браузера/произвольного файлового доступа у модели. Legacy-инструменты по прежним таблицам `public` не включаются. По прямому дополнению пользователя подключаются типизированное назначение стипендии через агента и запрос коррекции закрытой оценки через fn_request_grade_correction со специальным решением sp_decide_grade_correction. Прямой SQL-обход не допускается. Права, правила приказа и интеграция предметного рассмотрения с очередью ещё согласуются по разделу 5.5 актуального плана.

## 2. Существующие страницы и кнопки

| Страница | Чтение | Изменения, которые должен поддержать backend |
|---|---|---|
| Студенты | `v_student_summary`, карточка `student`, связанные lookup | Из формы только основа обучения, потребность в общежитии, иностранный статус. Остальное — существующие 6 workflows |
| Группы | `v_groups`; карточки/таблица, переходы к студентам/расписанию | Шифр, учебный план, куратор, староста, архив; создание и допустимое удаление |
| Расписание | `academic_term`, `v_schedule_calendar`, `holiday`, `pair_time`; таблица/неделя | `schedule_slot`: поручение, аудитория, день, пара, чётность, период. Изменяется слот на все его даты, не отдельный день |
| Курсовые и ВКР | `v_academic_works`, карточка `academic_work` | Студент, позиция плана, тема, руководитель, рецензент, приказ |
| Заявки на справки | `v_document_queue`, карточка `document_request` | Создать заявку, изменить допустимые реквизиты/статус/исполнителя, допустимое удаление. Для студента — только собственная заявка и разрешённые поля |
| Практики | `v_practice`, карточка `practice_placement` | Студент, позиция плана, руководитель, контакт организации, даты, приказ |
| Сотрудники | `v_employees`, карточки `employee` и связанной `person` | При создании выбирается существующая персона; при редактировании меняются её ФИО и реквизиты сотрудника. person_id после создания неизменяем; подтипы и действующие назначения проверяет БД |
| OLAP | Сейчас ComingSoonPage; восемь режимов есть в исходном макете | Полная реализация обязательна по прямому дополнению пользователя; недостающие формулы/API согласуются до разработки |

Каждое FK-поле получает тот lookup, который уже определён в `lookups.ts`. Backend отдаёт связи и понятные `description` в `/schema`; варианты поля `week_parity`, виды ведомостей и другие enum-подобные значения должны сохранять формат описаний БД, который разбирает `choicesOf`.

Фронтенд уже выполняет локальные поиск, фильтры, сортировку, размеры колонок и визуальную пагинацию. Backend отдаёт полную доступную выборку страницами `limit/offset`, сохраняет фильтры дат и сортировку календаря. Новые серверные отчёты/экспорты для этих действий не нужны.

## 3. Что остаётся в интерфейсе

Сохраняются login, данные пользователя в шапке, раскрываемый чат, список диалогов, переименование/удаление, копирование сообщений, вложения по чатам, отправка одних файлов с ожиданием готовности, полноэкранный просмотр документа, «Остановить», окно предложения с комментарием и нижние восемь вкладок. История/список/названия чатов становятся серверными; детали черновиков и удаления согласуются. Формы закрываются крестиком/Esc с вопросом о несохранённых данных; это клиентская логика.

Текущий исходный React хранит чаты в localStorage, но целевая серверная синхронизация прямо включена пользователем: после входа доступны свои беседы и полная сохранённая история. LocalStorage перестаёт быть источником истории чатов. Также подтверждено восстановление SSE после обрыва/перезагрузки: тот же run, пропущенные события/итог, без повторного запроса; «Остановить» — явная серверная команда. Перенос существующих данных, правила удаления/архивирования и точные новые контракты ещё согласуются; предметный аудит и официальные записи не стираются очисткой беседы.

После ручной записи frontend инвалидирует `res/row/lookup`. После подтверждения агента — те же запросы. Backend возвращает окончательное сохранённое состояние; это обеспечивает одинаковый вид результата в таблице независимо от способа выполнения.

## 4. Правила изменений

Проверяются границы роли/института, FK и полнота ключа, nullable/default, уникальность, статус и даты, учебный план группы, активность экзаменатора/сотрудника, соответствие вида работы/практики, вместимость и пересечения расписания, последовательность ведомостей и неизменяемость официальных записей.

В существующих работах, практиках и заявках нельзя сменить student_id; в существующем employee — person_id. У сотрудника допустимо менять только разрешённые поля ФИО связанной person. Два PATCH формы сотрудника не дают общей атомарности: если второй отклонён, первое изменение могло сохраниться; этот случай проверяется отдельно.

Закрытая оценка не редактируется напрямую. Не меняются `student.group_id/status_id` через PATCH. Финальная заявка и проведённый приказ соблюдают правила исходной схемы. Связанные справочники/журналы нельзя стирать ради прохождения DELETE. Любое окончательное изменение и его аудит атомарны.

Будущий приказ возвращает `status: pending` и `effective_date`; worker меняет состояние только в срок. Приказ на сегодня возвращает применённое состояние. Это именно статус приказа, а не статус предложения агента.

Ошибка отображается существующим `errors.ts`: безопасный код, сообщение и request_id. Устаревшее предложение требует нового запроса агенту, потому что текущий frontend не имеет отдельной кнопки обновления preview. Модель/поиск/БД имеют явные состояния отказа, без вымышленных результатов.
