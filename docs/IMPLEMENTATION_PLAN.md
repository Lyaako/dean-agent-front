# Полный план backend под утверждённый frontend

**Этот документ описывает базовые задачи до четырёх выбранных дополнений.** Актуальная спецификация для одобрения — [DETAILED_IMPLEMENTATION_PLAN.md](DETAILED_IMPLEMENTATION_PLAN.md): роли/кнопки, 14 этапов, очередь, передача, исполнение и manifest вложений. При расхождении действует новый план; реализация до одобрения не начинается.

## 1. Зафиксированный объём

Frontend из ветки **react-frontend** [Lyaako/dean-agent-front](https://github.com/Lyaako/dean-agent-front/tree/9c68ae0c5f062b87811058599151bc135576b33d/frontend) сохраняется. Зафиксирован commit `9c68ae0c5f062b87811058599151bc135576b33d`; [отличия версии](FRONTEND_VERSION.md). Backend поддерживает его существующие пути, тела запросов, типы, роль пользователя, вкладки, формы, чат и окно изменений. Из корневого [dean_agent](https://github.com/Ethenkam/dean-agent/tree/d92bf5fbfc5b37c3236a6454aeffa5374fe88b11/dean_agent) переносится весь действующий функционал агента, с заменой прототипной идентификации и доступа на проверяемые серверные права. `backend_dean` не является исходной реализацией и не учитывается.

Приложенная `deanery` сохраняется полностью: **56 таблиц, 312 полей, 83 внешние связи, 27 представлений**. Поля и связи проверены разбором SQL. Каталог: [DATABASE_CATALOG.md](DATABASE_CATALOG.md), машиночитаемый перечень: [resource-catalog.json](resource-catalog.json). Этот JSON описывает исходную схему, но не заменяет реальный `/schema` и не является миграцией.

Результат разработки — реально работающий агент и сервер всех текущих действий фронтенда. В этом пакете подготовлен план; ниже нет утверждения, что задачи уже выполнены. Отсутствие нового экрана не означает потерю чтения соответствующих данных агентом.

## 2. Связь каждого экрана с backend

| `chat/ChatBar`, `useChat`, `api/agent` | SSE-адаптер полноценного агента, владение сессией, capabilities | Работают вопросы, продолжение, этапы, результат, ошибки, остановка и отправка только файлов после их готовности |
| `chat/proposals/*` | Чтение proposal и решение с точным preview/status | Применение меняет БД один раз; отказ не меняет; таблицы обновляются существующей инвалидизацией |

Для всех форм общий backend, без самостоятельных сервисов студентов/практик/справок. Локальные поисковые фильтры, размеры колонок, сортировка и визуальные страницы не переносятся на сервер без необходимости.

## 3. Ресурсы и структура БД

### Обязательные чтения фронтенда

Основные представления: `v_student_summary`, `v_groups`, `v_schedule_calendar`, `v_academic_works`, `v_document_queue`, `v_practice`, `v_employees`.

Lookup-представления: `v_students`, `v_teachers`, `v_curriculum`, `v_schedule_hours`. Сырые разрешённые ресурсы: `student`, `study_group`, `schedule_slot`, `academic_work`, `document_request`, `practice_placement`, `employee`, `person`, `dean_office_staff`, `curriculum`, `study_program`, `specialty`, `study_form`, `classroom`, `academic_term`, `holiday`, `pair_time`, `organization_contact`, `organization`, `academic_order`, `position`, `funding_type`, `leave_reason`, `document_type`, `request_status`.

Остальные FK-lookup возникают из metadata предложения, например grade → grade_sheet, teaching_assignment → lesson_type, contact_person и другие. Их разрешённое чтение добавляется по фактической связи, не через произвольный доступ ко всем колонкам. Автоматическая проверка строит замыкание всех FK, отображаемых существующими формами и ProposalDialog, и обнаруживает недостающий ресурс/подпись.

Для агента доступны безопасные описания и чтение всей необходимой предметной структуры, включая остальные представления результатов, долгов, приказов, отпусков, стипендий, нагрузки и аудита. Все 56 таблиц присутствуют в миграциях/метаданных; их наличие не означает универсальный публичный CRUD. `app_user.password_hash`, закрытые персональные поля, чужие запросы и аудит не раскрываются модели.

### Записи форм

| Ресурс | Поля/действия формы |
|---|---|
| student | PATCH: funding_type_id, needs_dormitory, is_foreign; создание/смена группы/статуса только workflow |
| study_group | name, curriculum_id, curator_id, headman_id, is_archived |
| schedule_slot | assignment_id, classroom_id, weekday, pair_number, week_parity, term_id, valid_from, valid_to |
| academic_work | student_id, item_id, topic, supervisor_id, reviewer_id, order_id |
| document_request | student_id, document_type_id, copies, purpose, request_status_id, processed_by_id; completed_at вычисляет сервер/БД |
| practice_placement | student_id, item_id, supervisor_id, org_contact_id, start_date, end_date, order_id |
| employee | При создании person_id; personnel_number, position_id, employment_rate, hire_date, dismissal_date; person_id не меняется при редактировании |
| person, связанная с employee | PATCH last_name, first_name, middle_name; право на ФИО проверяется отдельно, паспортные/служебные поля недоступны |

`config.order` в RecordDialog задаёт порядок, а не whitelist: форма добавляет все `spec.write_fields`. Поэтому backend обязан точно ограничить write_fields, не публиковать identity/audit поля и не делать student.group_id редактируемым. Учитывается несовпадение insert/update: поля изменения родителей нельзя произвольно расширять; запрет проверяется сервером для конкретной операции. Недопустимые DELETE скрываются через operation_roles и всё равно запрещаются сервером.

Фильтрация lookup в браузере — удобство. Backend повторяет проверки группы старосты, вида curriculum_item, действующего преподавателя, института подписанта и области связанных записей.

В новой ветке `lockOnEdit` запрещает смену student_id у academic_work, practice_placement и document_request. Сервер и tools повторяют этот запрет независимо от клиента. Linked-поля сотрудника требуют metadata/read/update для person и запрета смены employee.person_id. Форма вызывает сначала PATCH person, потом PATCH employee: нельзя обещать одну общую транзакцию через два текущих HTTP-вызова.

### Шесть workflows

| Имя в frontend | Соответствие SQL | Параметры и результат |
|---|---|---|
| enroll_student | fn_enroll_student | ФИО, пол, дата рождения, контакты, group_name, funding, record_book, order_number, signed_by, effective_date?; person/student/order/order_student одной транзакцией |
| transfer_student | sp_transfer_student | student_id, group_name, order_number, signed_by, effective_date?; только допустимая группа того же института |
| grant_academic_leave | sp_grant_academic_leave | student_id, reason, start, end, order_number, signed_by; reason из lookup — **название**, переводится в нужный аргумент процедуры, не произвольный текст |
| return_from_leave | sp_return_from_leave | student_id, group_name?, order_number, signed_by, effective_date?; прежняя группа при отсутствии новой |
| expel_student | sp_expel_student | student_id, reason, order_number, signed_by, effective_date?; явное основание, текущие статусы и связанные эффекты по БД |
| reinstate_student | sp_reinstate_student | student_id, group_name, order_number, signed_by, effective_date?; только отчисленный студент и допустимая группа |

`signed_by` frontend уже передаёт числом, `group_name/funding/reason` из workflow lookup — строками. Не переименовывать поля в клиенте; преобразование происходит в серверном адаптере. `order_date` в форме зачисления отсутствует: сервер задаёт текущую дату оформления в Europe/Moscow; пустая effective_date означает сегодня, как написано в форме. Для подготовки агентом эта политика явно присутствует в preview, а не подменяет явно указанную пользователем дату.

Все workflows возвращают PK, order_id, effective_date и status. Для даты в будущем оформляются приказ/связи, состояние применяется worker в срок. Зачисление может заранее создать student со статусом «Зачислен», как предусмотрено fn_enroll_student; нельзя обещать, что до даты вообще не появится ни одна предметная запись. Номера приказов, основания и подписант проверяются, не генерируются моделью молча.

### Дополнительный инструмент только для уже существующих действий

`prepare_workflow(name, arguments, explanation, reason)` валидирует одно из шести имён и вызывает общую workflow-операцию в режиме preview. Это устраняет нынешний разрыв: root agent запрещает менять status/group через SQL, а frontend уже имеет такие кнопки.

Существующий `ProposalPreview` умеет только INSERT/UPDATE. Для workflow он показывает основную запись, changed_columns и связанные эффекты; дополнительные строки/приказ перечисляются в related_effects. Точные параметры операции хранятся на сервере; не добавляется новый тип карточки/новый экран. `sql_text` для workflow может быть пустым, поскольку frontend не использует его для исполнения. Не требуется правка временного окна ProposalDialog или общего дизайна.

`read_attachment_text(version_id, offset, limit)` подключается только при наличии обработанных вложений этого запроса. Он выдаёт страницы/фрагменты в пределах бюджета. Пользователь не получает доступ к файлу, просто назвав чужой UUID в сообщении. Capability выставляется true только после реализации и проверки пути file version → extraction → context → model.

Для необходимых операций форм, не входящих в SQL-whitelist таблиц или полей, `prepare_record_change` принимает только типизированные изменения person (ФИО), employee, study_group, трёх разрешённых полей student и допустимые правки остальных существующих форм вне SQL-whitelist полей: например item_id работы/практики, assignment_id/term_id слота. Используются те же проверки/исполнитель и текущий INSERT/UPDATE preview; для чтения/подтверждения не нужен новый HTTP-контракт. После создания неизменяемые parent ID не меняются. Исходный propose_sql_change остаётся ограничен своими десятью таблицами и наборами полей; свободный SQL для person и административных таблиц не открывается.

### Примеры полного рабочего поведения

1. «Покажи задолженности группы» → чтение v_debtors, таблица, источник и ограничения полноты. «Подготовь пересдачу» → уточнить дисциплину/этап, группу, экзаменатора и дату; проверяемый INSERT grade_sheet; решение сотрудника; реальная ведомость в БД. Само наличие долгов не доказывает допустимую следующую попытку.
2. «Создай справку студенту» → разрешённый student_id и тип документа, purpose/copies; preview; решение; та же строка, которую создаёт RecordDialog.
3. «Переведи студента» → все реквизиты приказа и группа; prepare_workflow; приказ через sp_transfer_student после решения; прежний статус не меняется простым UPDATE модели.
4. «Исправь оценку в открытой ведомости» → allowed grade UPDATE, проверка экзаменатора/группы и snapshot; закрытая ведомость возвращает запрет с объяснением штатной процедуры, без обхода триггера.
5. «Что говорит положение?» → hybrid поиск и источник/страница; отсутствующий документ не заменяется знаниями модели. Загруженное заявление распознаётся как заявление, а не как положение.
6. «Посмотри приложенный PDF» → обработанная версия, страницы, качество и границы покрытия; follow-up использует сохранённый текст и доступные refs, а не локальный путь браузера. Право на вложение перепроверяется на каждом чтении.

## 5. План работ и критерии завершения

### Шаг 1. Контракт и чистая база

- Зафиксировать ветку react-frontend и SHA обоих источников, сохранить frontend и его новый модульный макет без изменений; снять фактический перечень маршрутов/полей из его кода. Не смешивать файлы main и react-frontend.
- Поднять отдельную PostgreSQL БД и применить исходную схему/представления/seed/roles только там. Production-миграции создать отдельно, без DROP SCHEMA и демонстрационного пароля.
- Проверить 56 таблиц, 312 колонок, 83 FK, 27 views, составные PK, CHECK/UNIQUE/triggers/procedures. Запустить SQL-тесты, исправить несовместимости до сервисного кода.
- Создать metadata registry из whitelist, использовать реальные format_type/default/comments. Проверить полный набор псевдонимов из columns.tsx и обращений к r.* в карточках, WeekGrid и lookup.

**Готово, когда:** новая БД воспроизводима, SQL-проверки зелёные, ни одна колонка/frontend relation не осталась без соответствия. Самодельный JSON каталога не принимается за уже мигрированную БД.

### Шаг 2. Авторизация, область и чтение

- Реализовать login/refresh/logout/me с существующими ролями, проверкой хэша, активностью и лимитом попыток.
- Refresh rotation: hash токена, семейство сессии, истечение, отзыв при повторе; стабильный CSRF-token для данного семейства, который клиент хранит в localStorage. Проверять Origin на cookie-действиях; Bearer на API. Проверить две вкладки с Web Locks и отдельно ограничение fallback без этой возможности.
- Определять scope через реальные связи БД. Создать безопасные проекции для чтения формы/агента. Изолировать чужих студентов, институты, ведомости и файлы.
- Реализовать `/schema` и GET resources: типизированные фильтры, sort, limit/offset, has_more, стабильный порядок, чтение карточки и lookup.

**Готово, когда:** неизменённый frontend после login загружает все существующие страницы и lookup; tests с пятью ролями подтверждают изоляцию HTTP и SQL-инструмента. Read-only доступ не раскрывает секретные колонки.

### Шаг 3. Единые операции форм и приказы

- Реализовать POST/PATCH/DELETE семи основных таблиц форм через общие предметные функции и дополнительный PATCH person для ФИО сотрудника. Отдельно ограничить поля create/update, immutable PK/parent ID и служебные значения. Проверить частичное сохранение при успехе person PATCH и ошибке последующего employee PATCH, не вводить скрытую транзакцию между запросами.
- Реализовать шесть именованных workflows с точным преобразованием аргументов форм в fn/sp. Повтор Idempotency-Key сохраняет один приказ.
- Контекст `app.user_id`, `app.agent_request_id` ставить сервером локально в транзакции; для ручной формы agent_request_id отсутствует. БД создаёт audit_log/detail.
- Worker применения приказов: периодический поиск наступивших, блокировка студента/приказа, fn_apply_due_orders, атомарность, повтор после падения, состояние сбоя в служебном журнале.
- DELETE выдавать только для разрешённых независимых записей, не для студентов, проведённых приказов, audit и связанных справочников. Не выполнять каскадные очистки как обход зависимости.

**Готово, когда:** кнопки формы реально сохраняют данные и обновляют таблицы; противоречивые данные возвращают существующие frontend-коды. Будущий приказ применяется один раз в нужную дату.

### Шаг 4. Proposal и общая проверка preview

- Подготовка SQL/типизированной записи/Workflow использует тот же исполнитель в откатываемой транзакции. Сохраняются точные аргументы, before/after, зависимые строки, related_effects, автор, TTL и snapshot.
- GET/decision имеют точные формы API.md. Комментарий 10..2000; решение только допустимой staff-роли и области. Внутреннее состояние не расширяет union публичного status.
- При approve: block proposal и предметные строки в стабильном порядке, повтор прав/бизнес-правил/snapshot, изменение + audit + решение + idempotency result в одной транзакции.
- При reject: сохранить решение без предметного изменения. Expired/stale нельзя применить; следующий запрос агенту создаёт новый preview. Два одновременных решения не выполняют операцию дважды.

**Готово, когда:** настоящий ProposalDialog показывает diff/lookup/эффекты, подтверждает и отклоняет; повтор/гонка/устаревание протестированы на PostgreSQL. Агентское INSERT и ручной INSERT дают одинаковые предметные значения и ограничения.

### Шаг 5. Полноценный агент в API

- Перенести перечисленную действующую логику root agent. Подключить настоящий модельный провайдер; не заменять естественный язык regex-сценариями.
- Общий read/operation registry использовать во всех tools. SYSTEM_PROMPT хранит текущие ограничения, описание безопасной структуры, политику уточнения и запрет обхода подтверждения.
- Сохранять пользователя, session/messages/run и связь с agent_request. Удерживать одну активную генерацию на session между всеми API workers; отдельно ограничить concurrency пользователя и общую нагрузку.
- Добавить prepare_workflow, ограниченный prepare_record_change для действий существующих форм и безопасное чтение следующих фрагментов вложения. Сохранить query_deanery/propose_sql_change/search_regulations и согласованный tools_used. Принять запрос одних файлов: клиент уже подставляет message «Вложения: …»; факты берутся из проверенных версий, а не из имён файлов.
- SSE адаптировать к status/session/tool_call/tool_result/done/error с подтверждённым восстановлением по 5.6 актуального плана: сохранять упорядоченные события, переподключаться к тому же run без повторной генерации; явную Stop-команду отличать от разрыва связи. Точные контракты/хранение согласуются до реализации. Проверять таймаут модели и budget инструментов.
- Не помещать DSN/секреты/сырой traceback в trace. Перечень proposals получать из БД по данному run, не извлекать ID из Markdown ответа модели.

**Готово, когда:** реальная модель проходит русские сценарии чтения, уточнения, продолжения, нормативных ссылок и изменения; результат подтверждается вызванным tool/аргументами/БД. Весь действующий функционал root agent перенесён, старые public/legacy-инструменты не активны.

### Шаг 6. Файлы и нормативный поиск

- Upload немедленно возвращает file_id/version_id/job; приватный оригинал, SHA, размер, MIME, владелец, purpose. Проверка содержимого, quarantine/антивирус, ограничения распаковки/парсинга; failure отражается в Job.
- PDF: текст по страницам; DOCX: текст по абзацам с лимитами ZIP/XML; TXT: UTF-8 без бинарных управляющих символов. Сохранить корневой визуальный путь PDF/изображений и CSV как возможности парсера, без изменения текущего React selector.
- Предлагаемые исходные лимиты: 10 000 000 байт/файл, 20 000 000/запрос, 5 файлов; начальный текстовый контекст 60 000 символов и первые 10 визуальных страниц модели. Пользователь прямо добавил OCR всех сканированных страниц принятого PDF; его охват не ограничивается десятью страницами. Средство/лимиты согласуются по 5.7 актуального плана. Дополнительные текстовые/OCR-части доступны через version-bound инструмент; частичное распознавание явно обозначается.
- File context содержит filename, version_id, страницу/фрагмент, качество и сокращение. Только refs текущего запроса; повторные сообщения получают вложение по сохранённой связи и повторной проверке доступа.
- Регламентный импорт: версия документа, точный источник, извлечение, проверка качества, chunk/page, BGE-M3, Qdrant, публикация. Индекс хранит version_id, сервер перепроверяет её доступность/актуальность после поиска.
- Retry worker ограничен; lease и уникальность задания защищают от двойного результата. Публикация индекса не скрывает failed/partial обработку. Job status совместим с polling раз в секунду текущего клиента.

**Готово, когда:** файл проходит полный upload → job → download → chat → цитата цикл; нормативный поиск реально обращается к BGE/Qdrant и возвращает проверяемую версию. agent_supported=true соответствует проверенному пути, не декоративной галочке.

### Шаг 7. Проверка неизменённым фронтендом

- Запустить именно `frontend/` зафиксированного commit против нового backend, с его package-lock и настройкой VITE_API_TARGET. Не подменять клиент собственным макетом при E2E-приёмке.
- Пройти семь рабочих вкладок, карточки, фильтры, все lookup, CRUD, шесть workflows, login/refresh/logout в двух вкладках, чат, proposals и файлы на действительной БД. Дополнительно проверить linked ФИО сотрудника, неизменяемый student_id у трёх типов записей, закрытие несохранённой формы и отправку одних файлов с ожиданием job.
- Парами выполнить одну задачу через форму и агента: справка, курсовая, практика, расписание, перевод и правка ФИО сотрудника. Сравнить предметное состояние, ограничения и audit; источник действия должен различаться, сама операция — совпадать.
- Проверить пользователя из другого института, student/teacher, подменённые PK/FK, чужой file/session/proposal, direct PATCH group/status, closed grade, двойной decision, повтор workflow, model/Qdrant/DB down, broken file и prompt injection во вложении.
- По прямому уточнению пользователя реализовать серверный ChatStore вместо локальной истории: список/названия/сообщения доступны с другого устройства. Контракты и правила переноса/удаления предварительно согласуются по разделу 5.5 актуального плана. Остановка SSE не должна потерять или повторно применить уже подтверждённое изменение.

**Готово, когда:** ни один текущий frontend-вызов не изменён ради сервера, все необходимые действия проходят E2E, ошибки безопасно отображаются существующими компонентами. SQL-тесты и существенные контрактные/транзакционные тесты зелёные.

### Шаг 8. Развёртывание

- Compose: frontend/reverse proxy, API, worker, PostgreSQL, Qdrant, BGE-M3, приватный том файлов; модель — по доступному провайдеру. Прокси `/api` соответствует текущему vite.config.ts (по умолчанию backend 8010).
- Отдельные secrets/environment, production hash/password policies, HTTPS/cookie, доступность модели/индекса, request_id, длительность tools и ошибки jobs без утечки содержимого.
- Backup/restore PostgreSQL и оригиналов, восстановимая переиндексация Qdrant; проверка восстановления на отдельной БД. Выполнение миграций отдельной ролью.
- Документировать запуск, импорт положений, смену конфигурации, обработку failed jobs и восстановление; задать сроки хранения файлов/истории по правилам проекта.

**Готово, когда:** новый экземпляр поднимается из документации, принимает неизменённый frontend, восстановление проверено, фоновый приказ и файл переживают перезапуск процесса.

## 6. Минимальные обязательные проверки

| Группа | Что проверять, помимо успешного сценария |
|---|---|
| Контракт | Все routes/union statuses/nullable/type aliases, FK-lookup замыкание, comments/default, query filters и exception codes |

| Изменение SQL | Только разрешённые таблицы/поля, простой literal, single row; запрет опасных выражений/DELETE; no mutation до approve |

## 7. Ограничения фиксированного клиента

1. `fetchAll` прекращает загрузку после 40 страниц по 500, то есть 20 000 строк. Неизменный frontend может молча обрезать более крупную выборку. Backend не должен делать вид, что она полная: требуется ограничить рабочий объём/область и календарный период, а при превышении выдавать понятную ошибку до частичного успешного показа. Для крупных институтов понадобится отдельное согласованное изменение транспорта клиента; дизайн менять не требуется, но в текущий backend-only объём это не входит.
2. PATCH форм не содержит version/If-Match/исходных значений. Блокировка защищает транзакционную целостность, но не обнаруживает все устаревшие правки из двух браузеров. Для обычных форм сохраняется текущая семантика; надёжная защита от перезаписи потребует передачи версии клиентом. Для agent proposal snapshot доступен и обязателен.
3. Обычный POST resources не отправляет Idempotency-Key. Нельзя гарантировать exactly-once после повторной отправки неоднозначного сетевого сбоя. Реальные UNIQUE и транзакции остаются; ключ обязателен только там, где уже есть в клиенте — workflows/files/decision.
4. Исходный чат не имеет идентификации повторной отправки и восстановления SSE. Пользователь прямо включил переподключение к тому же run после обрыва/перезагрузки, без нового запроса/дубликатов. Контракт идентификации первоначальной отправки, replay и явной остановки должен быть отдельно согласован и подключён в клиенте/сервере по 5.6 актуального плана.
5. «Остановить» закрывает поток, а не отзывает транзакцию решения. Синхронный вызов модели может завершаться позже; новые tools после отмены блокируются, итог фиксируется внутренне. Автоматическое повторное выполнение запрещено.
6. React принимает только PDF/DOCX/TXT, хотя исходный root agent умеет дополнительные форматы. Они сохраняются в парсере; обещание выбора фото/CSV этим React-интерфейсом без его правки было бы неверным.
7. Серверная синхронизация бесед прямо включена; localStorage больше не источник истории. Перенос старых локальных данных, черновики и удаление/архивирование ещё согласуются. Предметный аудит/предложения не удаляются очисткой чата.
8. Форма сотрудника может отправить два PATCH. Если ФИО сохранилось, а employee PATCH не прошёл, нельзя откатить уже завершённый первый HTTP-запрос атомарной транзакцией второго. Это существующее ограничение новой ветки; каждый запрос сохраняет собственную целостность и аудит.
9. Клиент использует Web Locks для последовательного refresh между вкладками, а без поддержки этой функции выполняет запрос напрямую. При строгом отзыве семейства из-за повторного refresh token параллельные запросы такого fallback могут завершить сессию. Поддержка Web Locks и этот случай должны быть частью проверки целевых браузеров.

## 8. Что не добавлять

Новый UI, собственную стартовую страницу агента, отдельный каталог 56 CRUD-таблиц, дополнительные кабинеты знаний/аудита, управление пользователями/зарплатой/бюджетом, серверный экспорт, уведомления, мобильное приложение, оптимизатор расписания, автономные решения по отчислению, внешнюю ЭП/документооборот и отдельную сеть микросервисов. Они не требуются текущими frontend-вызовами или действующим root agent; оставшиеся вопросы рассматриваются по OPEN_DECISIONS.md. OCR всех сканированных страниц принятого PDF прямо добавлен пользователем и из исключений убран.

Базовый критерий полноты: **весь работающий функционал root agent + все существующие серверные обращения утверждённого frontend + вся исходная deanery-схема**, с общими операциями, реальными правами и проверяемым результатом в БД.
