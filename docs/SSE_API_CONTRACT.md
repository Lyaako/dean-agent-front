# Контракт восстановления SSE для прямого согласования

Статус: контракт P00 прямо подтверждён пользователем ответом «Подтверждаю контракт SSE». Восстановление того же run и хранение событий в agent_run JSONB также подтверждены. Здесь не выбираются сроки хранения, лимиты модели и восстановление после аварии самого сервера.

Все пути ниже находятся под существующим /api/v1; требуют действующего Bearer и проверки владельца run/session. Повторная подписка повторно проверяет доступ. Секреты/закрытые поля не попадают в события.

## Начальная отправка

Сохраняется POST /agent/chat/stream с прежним телом {message, session_id?, attachments?}. Клиент дополнительно отправляет Idempotency-Key: UUID одной отправки сообщения и сохраняет ключ до выяснения исхода отправки.

- Первая отправка атомарно фиксирует сообщение, run и привязку ключа к исходному запросу, затем начинает единственный запуск и выдачу SSE.
- Повтор с тем же пользователем/ключом/телом подключается к исходному run, не создавая новое сообщение, запуск модели или proposal. Это позволяет восстановиться даже при потере первого session event.
- Повтор ключа с другим телом получает существующий idempotency_conflict.
- Новая осознанная отправка сообщения использует новый ключ; запуск при занятой беседе получает session_busy.
- Обычные POST ресурсов не получают этот новый обязательный заголовок.

## Повторная подписка

GET /agent/runs/{run_id}/events?after={sequence} возвращает text/event-stream. After — неотрицательный номер последнего полностью обработанного события; 0 означает с начала.

- Каждое сохраняемое событие имеет строго возрастающий номер внутри run. В SSE он передаётся стандартной строкой id: <sequence>.
- Типы и data существующих событий status/session/tool_call/tool_result/done/error сохраняются. Серверные heartbeat-комментарии не расходуют номера событий.
- Сервер сначала выдаёт сохранённые события с номером больше after, затем новые события того же run. Завершённый run воспроизводит сохранённый конечный результат.
- Клиент фиксирует курсор после обработки события и игнорирует уже обработанный номер; карточки/сообщения/done повторно не добавляются.
- Событие фиксируется в agent_run JSONB до отправки подписчику. Отмена HTTP-соединения не отменяет run.
- Отсутствующий/недоступный run не раскрывает чужие данные. Автоматическое переподключение не повторяет модельные/предметные операции.

## Явная остановка

POST /agent/runs/{run_id}/cancel с пустым JSON {} принимает запрос остановки и возвращает 202 с {run_id, stop_requested: true}.

- Остановку может запросить владелец run. Повторная команда не создаёт вторую операцию остановки.
- Принимается серверный запрос остановки; новые tools после него не запускаются. Завершение уже начатого provider call может быть кооперативным.
- Прерывание fetch в браузере закрывает только соединение; оно не заменяет эту команду.
- Уже завершённый run не запускается/не отменяется заново: ответ 200 с {run_id, stop_requested: false}; ранее подтверждённая отдельная транзакция не отзывается.
- Сохранённое конечное состояние доступно через повторную подписку. Точный пользовательский текст конечного события остановки согласуется отдельно, без добавления нового обязательного типа события.

Отдельно подтверждены отсутствие автоматической очистки по возрасту и порядок удаления активного чата «Остановить» → дождаться завершения → «Удалить». При удалении очищаются копии переписки в событиях/ответах/cache; предложения и аудит сохраняются. Политика повторной отправки после утраты результата и бюджеты ещё согласуются.
