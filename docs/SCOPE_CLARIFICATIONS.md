# Уточнения объёма: OLAP, чаты, OCR, CRUD и предметные процессы

Этот документ отвечает на вопросы пользователя и фиксирует прямые уточнения объёма. Подтверждены полный OLAP, четыре определения его показателей ниже, полноценная серверная синхронизация чатов вместо localStorage, стипендии через агента при технической возможности, коррекция закрытой оценки через имеющиеся процедуры, восстановление SSE после обрыва связи/перезагрузки страницы, OCR всех сканированных страниц принятого PDF и отмена ещё не исполненного приказа для студента через агента с подтверждением сотрудника. Реализация ещё не разрешена. Остальные расширения/настройки рассматриваются по одному вопросу по [OPEN_DECISIONS.md](OPEN_DECISIONS.md); новые допущения/отступления требуют прямого подтверждения в чате.

**Окончательное решение об объёме:** пользователь подтвердил сохранение существующих возможностей и всех прямо согласованных дополнений, «остальное исключаем». Неподтверждённые функциональные расширения больше не рассматриваются для этого этапа; в частности, исправление ошибочной уже действовавшей стипендии не добавляется. Права, API, хранение и другие неутверждённые параметры включённых функций остаются на прямое согласование; это не новые функции и не разрешение выбирать их самостоятельно.

## OLAP

Полная реализация OLAP обязательна по прямому запросу пользователя. Исходный mockup/redesign/app.js содержит восемь режимов: roll-up группы/дисциплины/семестра, срез группы/дисциплины, dice, drill-down группы и кросс-таблица группа × семестр. Там есть таблицы, выборы, фильтры, графики средних и динамики, шкала и линия среднего. React пока содержит ComingSoonPage; это текущее состояние источника, а не целевая граница проекта.

Демонстрационный rollup считает долг по points=null, а исходный v_debtors собирает попытки итогового контроля у активного студента и проверяет отсутствие положительного результата по дисциплине. Подсчёт всех попыток и последних результатов v_last_result даёт разные средние и количества. Поэтому определения ниже были вынесены на согласование и подтверждены пользователем фразой «давай в олап пока эти».

**Подтверждённые четыре определения** для восьми режимов исходного макета:

| Показатель | Подтверждённое определение |
|---|---|
| Средний балл | AVG(points) по последним итоговым результатам v_last_result (stage=final), без NULL в среднем; не среднее по всем попыткам и не среднее из средних студентов |
| Количество результатов | Количество соответствующих последних итоговых записей, включая зарегистрированный результат с NULL, но без выдуманных записей для ещё не сдававших |
| На отлично | Среди этих итоговых результатов только graded контроль с fn_mark(points)=5, по реальному score_band |
| Долги | Количество соответствующих задолженностей v_debtors по его исходным правилам, а не количество всех NULL в попытках |

Округление, дополнительные фильтры студентов/статусов/периодов, точный API и способ интеграции агентом ещё требуют явной фиксации. Исходные условия самих v_last_result/v_debtors сохраняются. OLAP не требует автоматически нового хранилища/таблиц: такое решение пока не принято.

## Синхронизация чатов

Имеется в виду один серверный список бесед, названия и история, доступные после входа с другого браузера/устройства. Переименование/удаление/новые сообщения отражаются в этом общем списке. Это отличается от наличия server chat_session/chat_message для контекста модели: текущий React хранит список и видимую переписку в localStorage и не получает их с сервера.

**Теперь синхронизация прямо включена пользователем.** Сервер становится источником списка, названий и полной сохранённой переписки; localStorage перестаёт быть источником истории чатов. После входа с другого устройства пользователь получает свои беседы, сообщения, связи с файлами и предложениями, актуальные серверные решения. Переименование и удаление выполняются через сервер. Существующий интерфейс ChatStore позволяет заменить хранилище без нового дизайна чата.

Перенос старых локальных бесед, хранение черновиков, правила удаления/архивирования, сроки хранения и разрешение конкурентных правок ещё не выбраны. Их обсуждаем отдельно. Синхронизация сохранённых чатов сама по себе не восстанавливает прерванный SSE. Локальные настройки авторизации/CSRF не относятся к истории чатов и не удаляются этим требованием.

## Восстановление SSE

SSE — доставка событий работы агента от сервера в открытый чат. Полное восстановление означает после разрыва связи подключиться к тому же запуску, получить пропущенные события/ответ и продолжить отображение без повторного запуска и повторной предметной операции.

**Теперь пользователь прямо включил такое восстановление.** При обрыве связи/перезагрузке страницы серверный запуск продолжается, клиент подключается к тому же run и получает пропущенные этапы/ответ/предложения. Новая генерация и повторные предметные действия не запускаются; повторно доставленные события не дублируются в UI. «Остановить» отдельно посылает серверную команду остановки; прекращение fetch само по себе её не заменяет.

Текущий React этого ещё не реализует. Нужно согласовать точные маршруты, идентификаторы/курсор, сроки и место хранения событий, затем изменить сервер и клиент. Новая таблица автоматически не добавляется. Это восстановление связи с серверным run; автоматический перезапуск генерации после аварии самого сервера/провайдера отдельно не утверждён. Подробное поведение — раздел 5.6 актуального плана.

## OCR

OCR — распознавание текста сканированных страниц, где обычного извлекаемого текстового слоя нет. Извлечение текста цифрового PDF и передача отдельных страниц vision-модели не являются отдельным полным OCR всех страниц.

**Теперь пользователь прямо включил OCR всех сканированных страниц принятого PDF.** Цифровой текст извлекается напрямую, сканированные страницы распознаются фоново, включая страницы после десятой в смешанном PDF. Текст сохраняется с привязкой к версии/странице и доступен агенту фрагментами. UI показывает ход обработки, охват и ошибки страниц; отдельно показывает реально переданные/использованные агентом части.

Средство распознавания, языки и лимиты ещё согласуются; см. 5.7 актуального плана. Это не автоматическое расширение на DOCX-картинки/фотографии или операторский нормативный импорт. «Все страницы обработаны» и «каждый символ распознан верно» — разные требования. Неразборчивые/обрезанные страницы, рукопись, подписи и печати не позволяют обещать безошибочное восстановление любого оригинала.

## В каких таблицах нет полного CRUD

Здесь CRUD означает четыре операции над записью: создание, чтение, изменение и удаление. Даже для CRUD права, FK, история и состояние ограничивают допустимые действия. Чтение ниже означает разрешённые проекции/поля, а не выдачу секретов каждой таблицы пользователю.

| Группа | Количество | Точные таблицы | Доступ текущего плана и причина |
|---|---:|---|---|
| Четыре операции по условиям | 6 | study_group, schedule_slot, academic_work, practice_placement, document_request, employee | Существующие формы; удаление только допустимого независимого состояния. Агент создаёт/меняет, но не удаляет |
| Справочники | 20 | position, academic_degree, academic_title, education_level, study_form, funding_type, student_status, control_type, lesson_type, score_band, academic_term, holiday, pair_time, order_type, leave_reason, contact_relation, scholarship_type, document_type, request_status, app_role | Чтение/lookup, без новых редакторов. Отсутствие редакторов — прежний выбор объёма; многие удаления дополнительно блокируются ссылками |
| Структура и учебные настройки | 12 | institute, department, teacher, dean_office_staff, classroom, specialty, study_program, curriculum, discipline, curriculum_item, organization, student_contact | Чтение/lookup/существующие связи; нет формы и подключённого write-tool. Новое управление потребует явного расширения и предметных проверок |
| INSERT/UPDATE только агентом | 6 | contact_person, teaching_assignment, attendance, grade_sheet, grade, organization_contact | Подготовка предложений и чтение, без DELETE. Закрытые оценки/ведомости и неизменяемые связи ограничиваются БД |
| Процессы вместо свободного CRUD | 4 | student, academic_order, order_student, academic_leave | Student имеет три разрешённых PATCH-поля; создание/движение/приказы/отпуска — шесть workflows. Нет произвольного изменения проведённых приказов или удаления истории |
| Person с узким изменением | 1 | person | Создание как часть зачисления, чтение разрешённых полей, ФИО связанного employee; не произвольные паспортные/персональные правки и DELETE |
| Специальные предметные процессы | 2 | scholarship, grade_correction | Чтение и прямо добавленные действия через агента: назначение стипендии и запрос коррекции закрытой оценки с предметным рассмотрением. Точные правила новых контрактов ещё согласуются; свободный CRUD не добавлен |
| Учётные записи и служебные журналы | 5 | app_user, agent_intent, agent_request, audit_log, audit_log_detail | Учётные записи используются auth, намерения кодом, запросы оркестратором, аудит триггерами. Нет нового админского редактора; аудит защищён от ручной подмены |

Итого 56: у шести есть условные четыре операции, у остальных 50 — перечисленные ограничения. Отсутствие свободного CRUD нельзя приравнивать к отсутствию возможности добавить необходимое бизнес-действие. Исключение новых редакторов было интерпретацией прежнего запроса о поддержке имеющегося фронтенда, а не запретом самой схемы на любое развитие.

## Стипендии

Исходный root SQL tool не включает scholarship; React показывает стипендии в сводке, но не имеет формы назначения. Поэтому прежний план подключал чтение. Это неполнота выбранного функционального объёма, а не техническая невозможность.

В приложенных SQL есть scholarship, scholarship_type, ссылки на приказ и ограничения: назначение обучающемуся, бюджетный вид стипендии только бюджетнику; один вид одному студенту нельзя назначить на пересекающиеся периоды. Даты и приказ обязательны. Отдельной процедуры назначения/отмены стипендии в этом SQL нет; прежняя общая формулировка о «соответствующих процедурах» для всех трёх процессов была неточной.

**Работа через агента прямо включена пользователем и технически реализуема.** Требуется отдельное типизированное предметное действие: агент уточняет студента, вид, период и основание/приказ, готовит проверяемое предложение; запись появляется после решения уполномоченного сотрудника. Отсутствие такого tool в исходном репозитории не означает невозможности его подключить; запасное меню сейчас не выбирается.

**Досрочное прекращение действующего назначения также прямо добавлено.** Агент уточняет назначение, основание и новую дату окончания — последний день включительно; после решения сотрудника сервер проверяет актуальность/даты и сокращает end_date, сохраняя запись и историю. Модель сама не принимает решение по успеваемости. Права, приказ/контракты и ретроспективные даты ещё согласуются по 5.9.

**Отмена ещё не начавшегося назначения теперь тоже подтверждена.** Агент готовит отдельное предложение, сотрудник решает, сервер проверяет, что период не начался; отменённое назначение не активируется, история и другие назначения сохраняются. Конкретный способ хранения отмены и последствия для приказа ещё не выбраны по 5.10. Исходное end_date > start_date исключает подмену отмены концом перед началом. Исправление ошибочного уже действовавшего назначения ещё обсуждается отдельно.

## Коррекция закрытой оценки

Готовые fn_request_grade_correction и sp_decide_grade_correction есть. Прежний план не подключал их, потому что текущий React и root tools не содержат такого маршрута. Это не невозможность.

**Коррекция через агента прямо включена пользователем; нужные процедуры существуют.** Исходные правила требуют: работающий сотрудник подаёт заявку, преподаватель — по своей ведомости; рассматривает директор/замдиректора института группы, не автор. Проверяются неизменность исходной оценки и отсутствие более поздней попытки. Одобрение и изменение оценки выполняются в одной транзакции. Агент должен помогать определить ведомость/студента, новое значение/неявку и причину, затем использовать маршрут заявки, а не прямой UPDATE закрытой оценки. При отказе оценка не меняется.

Здесь нельзя применять общее предлагаемое самоподтверждение обычного proposal: предметная БД требует другого согласующего. Момент создания grade_correction и интеграцию предметного рассмотрения с общей очередью ещё следует отдельно согласовать, чтобы не добавить неоговорённое двойное подтверждение.

## Отмена планового приказа

Готовая sp_cancel_scheduled_order есть. Текущий frontend не имеет соответствующей кнопки, а агент — подключённого workflow/tool, поэтому прежний план не предоставлял действие.

**Теперь пользователь прямо включил отмену ещё не исполненного приказа для студента через агента и подтверждение сотрудника.** Агент уточняет приказ/студента/причину и готовит отдельное предложение с последствиями; сервер после решения повторно проверяет состояние и вызывает sp_cancel_scheduled_order. Процедура учитывает связанные записи отпуска/выхода, сохраняет других студентов и удаляет пустой приказ. История отмены должна переживать удаление предметных строк.

Для зачисления процедура прямо отказывает; приложение не обходит это удалением студента. Исполненное действие этим путём не отменяется. Точные права, tool/API и отображение отменённого исполнения ещё согласуются по 5.8 актуального плана. Реализация не начата.

## Девятая вкладка

Это означало отдельную новую нижнюю вкладку «Согласование» рядом с восемью существующими вкладками, включая OLAP. Никаких девяти таблиц или девяти очередей не имелось в виду. В текущем плане очередь размещается в существующей панели чата через «Чаты / На согласовании» и использует ProposalDialog; отдельная девятая нижняя вкладка не добавляется.
