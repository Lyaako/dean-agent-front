# Реализация согласованных изменений новой БД

Согласованные задачи Б1–Б11 из «План_изменений.docx» реализованы в backend. Текущая версия миграций — `0056_read_boundaries`, 56 предметных и16 служебных таблиц. Фронтенд выполняет коллега; его исходники в этой работе не менялись. Рабочая БД и прежний стенд на8443 не обновлялись: испытания проводились в отдельных базах.

Источник новой ревизии: [references/database-revision-20261011](../references/database-revision-20261011/source.json). Файлы вложения сохранены без изменений. Прежние references/database и миграции0001–0039 сохранены побайтно. Новый [каталог структуры](resource-catalog-revision.json) описывает текущую предметную схему; прежний resource-catalog.json остаётся историческим снимком.

## Выполненные изменения

- [x] Б1: 0040/032 доводит существующую схему до новой ревизии без пересоздания. Перед ограничениями проверяет паспорта, подписантов, повторных директоров, назначения с NULL-подгруппой, даты ведомостей, краевые пробелы/пустой запрос; выдаёт P4091 и перечень строк. Историческая сумма стипендии заполняется из вида стипендии. Перенесены225 проверок источника.
- [x] Б11: двенадцать отдельных кодов новых предметных ошибок, поле ошибки/ФИО отсутствующих оценок, request_id. Реальные SQL-диагностики проверены; пример SQL и имена функций исключаются из публичного сообщения.
- [x] Б2: идемпотентное создание личных NOLOGIN-ролей, привязка app_user.db_login, членство служебных LOGIN. Формы, процессы, решения и отмена исполняются с правами пользователя. Студент читает под deanery_read, пишет собственную заявку под deanery_agent с app.user_id=app_user.user_id. Агент читает/готовит под deanery_agent; фоновые приказы — под ним же без заявленного пользователя. Контекст восстанавливается; отложенные ограничения проверяются до выхода из личной роли.
- [x] Б3: employee только читается; person меняет только ФИО; 11 разрешённых справочников создаются/меняются; учётные записи читаются только admin без паролей; журнал ограничен институтом и не раскрывает чувствительные поля. Фильтрация/пагинация списков выполняется в PostgreSQL, включая полную базу результатов свыше20 тысяч записей.
- [x] Б4: обычные формы ведомостей, оценок и посещаемости; экзаменатор/занятие проверяются на сервере, чужие записи преподавателю недоступны для правки. Даты, баллы, закрытие и отсутствие оценок проверяет сама БД; missing показывает активных студентов основной ведомости без записи.
- [x] Б6: собственные результаты, долги, текущие модули, действующие стипендии с суммой назначения, приказы и посещаемость студента. Текущий модуль учитывает текущую группу и последнюю попытку. Своя новая заявка меняется только в copies/purpose; удаление студенту запрещено. Деканат удаляет заявки любого статуса в своей области.
- [x] Б7: одноразовый случайный временный пароль, отзыв сеансов, обязательная смена, собственная смена/выход везде/профиль. Подробные сервисы видит только admin. Проверка пароля и смена сериализованы с административным сбросом в одном порядке блокировок.
- [x] Б8: действующие подписанты своего института, пустая дата трактуется как сегодня, прошедшая запрещена, будущие приказы сохраняют отложенное исполнение. Отмена неисполненного приказа сохраняет журнал и отменяет фоновое задание. Исполнитель использует разрешённую публичную функцию БД, без выдачи права на её внутреннюю функцию.
- [x] Б10: session, heat, risk, retake, moves в дополнение к восьми прежним режимам. Область преподавателя — его учебные группы. Итоговые результаты и долги берутся из native views; риск включает null либо хотя бы один показатель ниже порога. Недостающая посещаемость не подменяется нулём.
- [x] Б5: форма коррекции с основанием10–2000 символов создаёт поданную заявку в существующей очереди. Решает другой действующий директор/заместитель института, включая admin только при реальной должности. Отсутствие подходящего руководителя возвращает явную ошибку. Деканат создаёт пересдачу/индивидуальную ведомость через обычный ресурс.
- [x] Б9: 14-й инструмент prepare_batch_changes, пакет1–200 строк, отдельные состояния строк, выбор picked_item_ids, атомарная запись и stale_item с номером. Преподаватель подтверждает собственные открытые оценки/посещаемость. Отмена до15 минут создаёт и сразу применяет обратное предложение того же решающего; вставки/необратимые поля пропускаются, позднейшие изменения обнаруживаются по снимку и аудиту. Конкурирующая ручная правка сохраняется. Повторы существующего ключа не выполняют второй эффект.
- [x] Регрессия, чистая установка, обновление старой базы и документация. Результаты: [qa/revision-20261015-results.json](qa/revision-20261015-results.json).

Подробный контракт для фронтенда находится в начале [API.md](API.md), включая точные типы items/field, новые маршруты, параметры OLAP и коды ошибок. Модель не получает инструмент подтверждения, исполнения или отмены.

## Явно разрешённые исключения к исходной БД

Пользователь отдельно одобрил только два узких дополнения к новой базе:

1. `deanery.fn_check_slot(INT)` выполняется SECURITY DEFINER с закреплённым безопасным search_path; EXECUTE разрешён deanery_staff/deanery_agent. Исходная проверка читала недоступные поля person и не позволяла сохранить расписание под личной ролью. Функция проверяет данные; права на запись таблиц не расширяются.
2. `grade_correction.reason` расширен с VARCHAR(500) до VARCHAR(2000), чтобы принять согласованный контракт формы. Зависимое native view v_grade_corrections пересоздаётся с прежними определением, владельцем, комментарием и ACL, без CASCADE. Неизвестная дополнительная зависимость останавливает миграцию.

Больше права предметных ролей и внутренние процедуры источника для обхода отказов не расширялись. Служебные права backend_api/agent_backend обеспечивают приватные сессии, очередь и подготовку. Для ограниченных native-привилегий агента проверка предложения сотрудника может временно использовать его личную роль **только внутри обязательного отката preview**; реальная запись ждёт отдельного решения и выполняется личной ролью решающего.

Прежние решения сохраняются: root contact_person/organization_contact меняет только admin; новое назначение стипендии начинается сегодня или позже. Перенос исторических данных с прошедшими датами не равен новому назначению.

## Что проверено 15.10.2026

Полный backend + переносимая упаковка: **480 passed, 7 skipped, 372 успешных subtests** за176,38с. Автономный прогон без БД:337 passed,150 skipped,157 subtests. Отдельная готовая к публикации копия без приватного env рабочего каталога прошла338 тестов/157 subtests с150 явными пропусками (включён последний дополнительный тест ИЛИ). После последнего усиления блокировки отмены и добавления теста логики риска: дополнительно10 passed/5 subtests. Пропуски обозначены явно: отдельные provider/attachment/calibration smokes, исторический operator-race harness и Linux parser/OCR. Новые OCR/нормативные сценарии этой задачей не менялись и заново через UI не принимались. Есть одно предупреждение устаревания per-request cookies в тестовом клиенте, без отказа приложения.

## Перенос и обновление существующей базы

Для новой машины используйте [GETTING_STARTED.md](GETTING_STARTED.md). Для существующей базы:

1. Остановите API/рабочие процессы, сделайте и проверьте резервную копию по [OPERATIONS.md](OPERATIONS.md). Сначала обновляйте копию. Исходный `01_schema.sql` содержит DROP SCHEMA: **не запускайте его для обновления**. Не запускайте bootstrap/seed на существующих данных.
2. Проверьте текущую версию и сохраните приватные подключения. Миграции выполняет существующий отдельный владелец backend_migration через служебный migration LOGIN: `python -m backend.db.upgrade_local <private-migration.json>`. Head0056 добавляет17 forward-only миграций к0039. Откат схемы вниз намеренно запрещён; восстановление — из проверенной резервной копии либо новая исправляющая миграция.
3. При P4091 изучите details с ключами/ctid и исправьте конкретные данные с оператором, затем повторите. Миграция не удаляет и не исправляет ошибочные строки молча. Дополнительные зависимости v_students/v_grade_corrections без CASCADE тоже требуют явного разбора.
4. После миграций и создания/проверки ограниченных служебных LOGIN запустите **владельцем базы** `python -m backend.db.provision_personal_roles <private-admin.json>`. Повторять после добавления/изменения активных сотрудников. Выполняется также при runtime/synthetic-seed чистой установки. Не запускайте вместо владельца обычным API LOGIN. Если уже существующая личная роль имеет LOGIN/привилегированные атрибуты, операция остановится.
5. Повторите калибровку по текущему приватному env для точного endpoint и14 инструментов; прежний13-tool fingerprint не подходит. Для Docker нужен собственный адрес host.docker.internal. Инструкция measure/apply находится в GETTING_STARTED; новый генератор намеренно выставляет нулевой fingerprint и требует измерения.
6. Запустите сервисы и проверьте readiness, вход пяти ролей, профиль, собственные данные студента, сохранение формы с правильным аудитом, предложение/подтверждение. Прогон тестов: `.venv/Scripts/python.exe -m pytest backend/tests deploy/test_packaging.py deploy/test_portable.py -q -p no:cacheprovider`; TEST_DATABASE_DSN задаётся только на отдельную мигрированную и засеянную тестовую БД. Без него SQL-случаи явно пропускаются.

Секреты, реальные данные, модели, временные базы/контейнеры и полные приватные журналы не входят в Git. В репозитории — исходники, неизменные исходные SQL, миграции, новая синтетическая seed, lock-файлы, контракты, публичное обезличенное доказательство и инструкции.

## Оставшиеся границы

Новый фронтенд коллеги не подключён: кликовая приёмка его кнопок/экранов остаётся следующим этапом после подключения. Исторические109 случаев12 октября относятся к прежней версии и не заменяют эту проверку. Публичный общий прогон не означает проверку всех естественных формулировок модели или производственной нагрузки. OLAP сохраняет лимит100000 фактов, обычные resource PATCH не имеют оптимистической версии, resource POST — ключа идемпотентности. Механизм исполнения консервативно блокирует связанные таблицы; массовая параллельная нагрузка отдельно не измерялась.
