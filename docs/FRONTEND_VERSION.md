# Версия утверждённого фронтенда

Рабочая основа: **ветка react-frontend**, commit **9c68ae0c5f062b87811058599151bc135576b33d**. [React-исходники](https://github.com/Lyaako/dean-agent-front/tree/9c68ae0c5f062b87811058599151bc135576b33d/frontend), [макет этой версии](https://github.com/Lyaako/dean-agent-front/tree/9c68ae0c5f062b87811058599151bc135576b33d/mockup/redesign).

Ветки расходятся: react-frontend содержит три новых коммита относительно общего предка, main — один свой. Поэтому новый frontend берётся целиком из указанной ветки, без смешивания её файлов с main. Коммиты обновляют React, затем приводят макет к React и добавляют версии в URL ассетов для обновления кэша.

`references/frontend-source/source.json` фиксирует репозиторий, ветку, SHA и файлы макета. `prototype` содержит точные копии десяти файлов этой версии. Проверка сравнивает их SHA-256 и синтаксис всех локальных JS. Это исходный макет с заглушками, а не альтернативный дизайн и не реализованный backend.

## Изменения, влияющие на backend

| Изменение frontend | Что требуется от backend |
|---|---|
| ФИО существующего сотрудника правится вместо выбора person | Разрешённый GET/PATCH person по person_id, только поля last_name/first_name/middle_name и только в допустимой области. Employee.person_id неизменяем после создания |
| У работ, практик и заявок заблокирована смена студента | student_id разрешён при создании, запрещён для смены существующей записи; проверка обязательна на сервере и в инструментах агента |
| Черновики и вложения отдельны для каждого чата | Проверять конкретные file/version refs каждого запуска; не использовать все недавно загруженные файлы пользователя как контекст |
| Можно отправить только файлы | Клиент сам формирует непустое message вида «Вложения: …»; сервер принимает такой запрос и реально читает версии, а не только имена |
| Отправка может ожидать окончания обработки файлов | Job должен честно переходить в succeeded/failed; до готовности версия не становится контекстом агента |
| Общая refresh cookie между вкладками, CSRF в localStorage, Web Locks | Проверять последовательную ротацию токена, стабильный CSRF и работу двух вкладок; access token остаётся в памяти каждой вкладки |
| Новые проверки чисел/дат в формах | Повторять проверки на сервере; возвращать существующие безопасные error codes. Клиентские проверки не защищают БД |
| Несохранённая форма предлагает сохранить/отбросить изменения | Существующие CRUD/workflow endpoints сохраняются; сохранение из этого окна не требует нового маршрута |
| Неделя управляет и таблицей расписания | GET календаря остаётся по семестру с текущими фильтрами; выбранную неделю frontend фильтрует локально. Новый week endpoint не нужен |
| Копирование сообщения, логотип, новые значки и окна | Это функции frontend; новые backend-маршруты для них не добавляются |

Пути и структуры auth/resources/workflows/chat/proposals/files остались прежними. Существенное дополнение для записи — PATCH person из формы сотрудника.

## Ограничение сохранения сотрудника

RecordDialog сначала посылает PATCH person, затем, если менялись реквизиты сотрудника, PATCH employee. Это **два отдельных HTTP-запроса**. Каждый обязан быть атомарным и проверяемым, но backend не может объединить оба в одну транзакцию через нынешний контракт. Если второй запрос отклонён, ФИО уже может быть сохранено. Этот случай входит в приёмку и не скрывается обещанием атомарного сохранения всей формы.

Дизайн и вызовы frontend в этом этапе не меняются. Остальные ранее описанные ограничения — bulk-лимит, отсутствие версии в PATCH, идемпотентность обычного CRUD и восстановление SSE — сохраняются.
