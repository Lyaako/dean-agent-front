# Коррекция закрытой оценки: контракт для согласования

Статус: контракт и правило срока прямо подтверждены пользователем ответом «Подтверждаю контракт и срок». Порядок «черновик → автор подаёт заявку → директор/замдиректора решает» и исходные процедуры БД также подтверждены. Этот документ раскрывает новые tool/API и срок черновика/предметной заявки.

## Подготовка

Типизированный инструмент prepare_grade_correction принимает {sheet_number, record_book, new_points, new_is_absent, reason}. Имена соответствуют аргументам fn_request_grade_correction без префикса p_. New_points может быть null; new_is_absent — обязательный boolean. Сочетание ненулевых баллов и неявки запрещено исходной grade. Причина обязательна, модель её не выдумывает.

Инструмент только готовит предложение и откатываемый preview. В постоянной grade_correction ещё нет заявки, оценка не меняется. Preview показывает существующую оценку/неявку, запрошенное значение, ведомость, студента и причину. Права/закрытая ведомость/шкала/более поздняя попытка проверяются исходными правилами плюс серверной областью.

GET /agent/proposals/{id} сохраняет старые поля и для этого вида добавляет kind: grade_correction, submission_status: draft|submitted, correction_id: integer|null. Эти поля не заменяют status: pending|approved|rejected. Draft виден автору в «Мои», а в директорскую очередь поступает после подачи.

## Подача автором

POST /agent/proposals/{id}/submit, JSON {expected_version}, Bearer и Idempotency-Key. Возвращает обновлённый Proposal.

- В окне черновика автор видит кнопку «Подать заявку» вместо обычного подтверждения изменения. Подать может только автор с действующим правом на запрос; студент не подаёт, преподаватель — только по своей ведомости.
- Сервер под контекстом автора повторно проверяет исходный результат, условия и snapshot, затем вызывает fn_request_grade_correction.
- Создание предметной заявки, связь correction_id, submission_status и событие подачи атомарны. Повтор запроса не создаёт вторую заявку.
- Submitted направляется в общую очередь допустимых директора/замдиректора соответствующего института. Обычный сотрудник деканата не получает права решения. Наличие роли admin само по себе не обходит fn_manages_institute.

## Решение руководителя

Используется существующий POST /agent/proposals/{id}/decision с {approve, reason, expected_version} и Idempotency-Key.

- Решать можно только submitted, после допустимого назначения/взятия по специальной предметной политике. Решающий — директор/замдиректора института, отличный от заявителя.
- Сервер вызывает sp_decide_grade_correction под контекстом согласующего. Одобрение, изменение grade и финальное состояние proposal фиксируются одной транзакцией; отказ сохраняет оценку.
- Preview и параметры заявки не редактируются. При изменившейся исходной оценке/более поздней попытке одобрение отказывает; повторный decision не применяет изменение дважды.
- Старые общие права self-approval обычных proposals не распространяются на коррекцию.

## Предлагаемый срок

Черновик до подачи ограничен общим TTL предложения (24 часа из плана) и повторной проверкой snapshot. После фактической подачи grade_correction это предметная заявка, возможность её рассмотрения не прекращается только из-за TTL черновика. Она остаётся в очереди до решения, с проверками исходной БД. Это уточнение общей TTL-политики прямо подтверждено пользователем вместе с контрактом.

Дополнительная таблица не нужна: draft/submission/correction_id — поля proposal, предметная заявка — исходная grade_correction, журнал — proposal_event и исходный аудит. [План](DETAILED_IMPLEMENTATION_PLAN.md), [процедуры](../references/database/02_views_functions.sql).
