## Запуск и учётные данные

Используется утверждённый React и отдельный Compose-проект `deanery-p13`. Порядок подготовки приватных каталогов, HTTPS и свежей PostgreSQL приведён в `deploy/README.md`. Единственная опубликованная точка нового приложения — `https://localhost:8443`; база и внутренние сервисы не публикуются в сеть.

Развёртывание разделено на начальную административную настройку, миграции и обычную работу:

- Временный административный пароль используется только для создания нового экземпляра PostgreSQL и отдельных входов. После настройки контейнер БД пересоздаётся с тем же PGDATA без этого секрета в его окружении и mounts.
- Миграционный вход имеет отдельную роль. API, исполнитель агента, обработчики файлов, нормативов, приказов и оператор нормативов получают собственные ограниченные подключения. Пароль администратора не является рабочим подключением приложения.
- Демонстрационный seed не содержит пригодных паролей пользователей. Явный шаг synthetic-seed в новой пустой БД создаёт приватные пароли трёх тестовых учётных записей. Файл с ними не входит в образы и исходники.
- Фронтенд обращается к `/api/v1` того же origin. Refresh cookie имеет Secure/HttpOnly; режим незащищённой cookie используется только отдельным локальным HTTP-стендом, не HTTPS-развёртыванием.

Обычная команда `up` до подготовки секретов, миграций и проверки ресурсов не заменяет эту последовательность. Для каждого вызова Compose указывается явный проект, приватный env-файл и все три Compose-файла в согласованном порядке.

## Как определить готовность

`GET /api/v1/health/ready` проверяет подключение API к БД, рабочую роль и наличие необходимых разрешённых функций. Ответ 200 означает готовность форм. Недоступность БД или необходимых функций даёт 503; модель для этой проверки не вызывается.

Авторизованный `GET /api/v1/agent/capabilities` отдельно показывает состояние модели, калибровки, BGE, индекса и четырёх обработчиков. Отсутствующий или пустой индекс не означает доступный нормативный поиск. Недоступная модель не выключает формы. Статусы не являются обещанием успешного выполнения следующего документа или запроса.

Обработчик обновляет свой приватный marker после успешного обращения к БД или продления действующего lease. Отсутствующий, повреждённый, будущий или старше 45 секунд marker означает unavailable. Пустая очередь при живом обработчике означает ready. API читает markers только для чтения; каждый обработчик пишет только собственный каталог.

Логи API и обработчиков содержат время, безопасный код события, длительность и известные request/run/job/proposal IDs. Для HTTP сохраняется шаблон маршрута, а не строка запроса. Пароли, токены, пользовательский текст, содержимое документов и сырые исключения в эти логи не включаются. Завершение HTTP приёма запуска не означает завершение работы модели.

Для нормативов используется существующий BGE-M3 с зафиксированной ревизией и dense/sparse индекс Qdrant. Второй экземпляр BGE без проверки памяти не запускается. Импорт и переиндексация выполняются существующим CLI с ограниченным операторским подключением и токеном действующего администратора приложения:

```powershell
docker compose @p13Compose run --rm operator python -m backend.regulations get-version $versionId
docker compose @p13Compose run --rm operator python -m backend.regulations reindex $versionId --key $operationKey
```

`$p13Compose` задаётся по `deploy/README.md`; `$versionId` — существующая разрешённая версия, `$operationKey` — UUID конкретной операции. При повторе той же операции используется прежний ключ. Токен находится в приватном файле и не передаётся строкой команды. Публикация поколения происходит после подтверждённой обработки и записи индекса; создание задания ещё не означает опубликованный источник.

## Согласованная резервная копия

Для P13 используется остановка записи на время резервирования. Это локальная процедура с паузой обслуживания, а не заявленная непрерывная online-копия.

1. Проверить имя и labels именно своего Compose-проекта. Сохранить текущие IDs образов, версию миграций, перечень исходных файлов, состояние очередей, предложений и приказов. Сначала закончить либо явно остановить свои активные пользовательские запуски. Незавершённые задания и leases фиксируются как незавершённые, не переписываются в succeeded.
2. Остановить только API и обработчики agent/file/knowledge/order этого проекта. На время копии не запускать операторский импорт. PostgreSQL остаётся работающей. Остановка только API недостаточна: работающий обработчик может менять БД и файлы.
3. Создать новый приватный каталог копии. Снять custom-format `pg_dump` всей прикладной БД и `pg_dumpall --roles-only` того же выделенного экземпляра. Копия ролей содержит чувствительные сведения и хранится вместе с приватными секретами, не в Git/образах/общем логе. Не использовать `--no-owner` или `--no-acl`: владельцы SECURITY DEFINER функций и узкие grants являются частью работоспособности и безопасности.
4. Скопировать `originals`, `regulations` и `derived` в новый каталог, проверить размер и SHA-256 каждого файла. Входные и выходные пути должны разрешаться внутри предназначенных приватных корней; ссылки наружу не обходятся. Сохранить метаданные подключений и модели отдельно как приватную часть копии. Health markers не переносятся: готовность должен доказать новый процесс.
5. Сохранить SHA-256 дампов и manifest файлов, контроль числа строк и состояния служебных сущностей. Проверить успешный код каждого инструмента. Дамп передаётся как бинарный файл, без текстового преобразования оболочкой. Qdrant не копируется: его данные восстанавливаются из проверенных версий нормативов.
6. Только после успешного сохранения всех частей возобновить нужные исходные сервисы. При ошибке сохранить частичные артефакты и явный failed-результат; неполная копия не становится пригодной резервной копией.

Автоматическая очистка по возрасту не включена. Ротация копий и период резервирования в текущем плане не настроены и не подразумеваются этой ручной процедурой.

## Восстановление в отдельном окружении

1. Использовать новый проект `deanery-p13-restore` с отсутствующим PostgreSQL volume и отдельными новыми каталогами files/secrets/health. Исходный проект и его данные не удалять. Перед восстановлением проверить SHA-256 копии.
2. Инициализировать отдельный PostgreSQL под новым уникальным bootstrap-пользователем БД. Это позволяет восстановить полный набор исходных ролей, включая postgres, без конфликта с уже созданным одноимённым пользователем. Bootstrap credential остаётся приватным и не становится подключением API.
3. Восстановить роли, затем custom dump в пустую БД штатными инструментами PostgreSQL. Любая неожиданная ошибка останавливает процедуру. Не применять `--clean`, массовый DROP или восстановление поверх существующей БД. Сохранить владельцев объектов и ACL. Не запускать seed поверх восстановленных данных.
4. Восстановить original/derived файлы и приватные подключения только в новом окружении. Проверить фактическую версию миграций, 71 прикладную таблицу плюс alembic_version, контрольные строки/последовательности, состояния чатов, предложений, заданий, приказов, аудит и SHA-256 файлов. Проверить владельцев SECURITY DEFINER функций и рабочие grants. Одинаковое число таблиц само по себе недостаточно.
5. Поднять отдельный пустой Qdrant. Для разрешённых опубликованных версий поставить реальные reindex-задания через оператора и обработчик. Использовать существующий BGE при подтверждённой доступности и достаточной памяти. Дождаться подтверждённой публикации новых поколений; проверить поиск, scope и отсутствие отозванных источников. Старые live points не являются источником восстановления.
6. Проверить приложение через отдельный loopback endpoint, защищённые файлы, очередь, историю и продолжение SSE. Приватный самоподписанный сертификат требует исключения только в тестовом клиенте; системное доверенное хранилище не изменяется.
7. Проверить завершение допустимых оставшихся заданий без повторного применения уже подтверждённых операций. Сохранить артефакты сравнения до/после. Переключение пользователя на восстановленный экземпляр является отдельным эксплуатационным действием, не побочным эффектом проверки восстановления.

## Перезапуск и неоднозначный результат

- Перезагрузка страницы или разрыв SSE не отменяет запуск. Клиент продолжает чтение сохранённых событий по run ID и последнему номеру; одна отправка сохраняет Idempotency-Key. Явная остановка выполняется отдельным маршрутом cancel.
- Перезапуск API не исполняет модель повторно. Истёкший lease запуска с неизвестным результатом отражается как `agent_outcome_unknown`; автоматического повторного вызова провайдера с возможным дублированием предложения нет.
- File/knowledge jobs используют существующие lease, checkpoint и ограничение попыток. Перезапуск обработчика не делает исходный файл новым и не объявляет частично прочитанный документ полностью прочитанным.
- Решение сотрудника и исполнение различаются. Будущий приказ сохраняет scheduled до применения; failed остаётся видимым с причиной. Повтор решения или повтор работы обработчика не должен повторно применить приказ.
- Удаление активного чата требует сначала явной остановки. Физическое удаление очищает переписку и её копии по согласованному контракту, сохраняет предложения и официальный аудит. Оно не является отменой приказа или предложения.

Фактически приняты API/SSE restart/replay и остановка/restart agent/file/knowledge/order. После45s остановленных markers capabilities показывает unavailable, формы продолжают работать; после запуска все8 статусов возвращаются в ready. Состояние будущих приказов, их jobs и аудит до/после совпали. Используйте `up -d --no-deps` для именованных сервисов: `start` требует сохранённого завершённого migrate container, а одноразовый мигратор удаляется.

В отдельном окружении P13 уже пройдена проверка HTTPS через настоящий reverse proxy: защищённые cookies, CSRF, роли, два клиента одного серверного чата, повтор отправки с прежним ключом, перезапуск API и восстановление тех же событий. Первое событие получено через 4,19 с, heartbeat — через 16,532 с от отправки. После явной остановки и удаления чата проверена очистка копий переписки в БД. Вызовов модели в этом испытании не было; это не проверка восстановления самого обработчика агента.

Для отдельной приёмочной среды подготовлен `backend/tests/integration/p13_recovery.py`: `backup` требует содержательных данных файлов, нормативов, предложений и заданий, останавливает только писателей исходного P13 и затем возобновляет те же контейнеры; `restore <имя приватного каталога копии>` отказывается использовать существующий проект/volume и сверяет все72 таблицы, последовательности, владельцев функций и grants. Фактический backup прошёл: custom dump и роли переданы бинарным потоком, сохранены provenance образов и SHA-256 файлов, контрольное состояние БД до/после совпало. Первая неудачная копия без complete marker не пригодна для restore. Фактическое restore прошло:72 таблицы/contents/owners/effectiveACL/sequences/11file hashes совпали.
